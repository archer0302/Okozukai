Two proofs and one documentation append. Both proofs run under the throwaway
`okozukai-verify` project so the real volume is never involved, and both use a scratch `.env`
that is restored afterwards.

**Proof A — a password containing keyword-value delimiters authenticates end to end.** Back up
the local `.env`, then write a scratch one whose password contains **both** a semicolon and an
equals sign. In `ConnectionStrings__okozukai`, the password must be wrapped in double quotes —
`Password="…"` — because the connection-string grammar is `keyword=value;keyword=value`, so an
unquoted delimiter inside a value either fails to parse or, worse, truncates the password at the
delimiter and authenticates with a partial value nobody intended. `POSTGRES_PASSWORD` takes the
same password **without** the double quotes: it is not a connection string, it is a single value,
and quotes there would become part of the password itself. Those two facts are the whole trap.

Bring the stack up on a fresh volume and assert three things: `/health` returns 200 with
`Healthy` (which exercises the PostgreSQL check, so authentication genuinely succeeded rather
than the app merely starting); `GET /api/journals` returns 200; and the quotes survived compose's
`env_file` reader into the container's environment. For that last one, count occurrences rather
than printing the value — the credential must not be echoed into a log or a transcript.

The mechanism being tested: compose's `env_file` reader strips quotes that wrap an *entire*
value, not quotes appearing inside one. The connection string's value starts with `Host=`, so
nothing wraps it, and the inner quotes reach Npgsql intact. That is the assumption RESEARCH.md
flagged; this proves it on this machine with this compose version rather than inheriting it.

**Proof B — the deployed stack cannot start in Development.** With the stack down, add
`ASPNETCORE_ENVIRONMENT=Development` to the scratch `.env` — simulating an operator who copied a
development file onto the box. Bring the stack up on a fresh volume and assert that the running
container still reports `Production`, that no seed log line appears, and that `Journals`, `Tags`
and `Transactions` are all empty. Compose's `environment:` block wins over `env_file:`, which is
why plan `02-01` pinned the value there rather than documenting it in `.env.example` and hoping.
This matters because the development seed path deletes every tag and journal before writing its
samples, guarded only by a zero-transaction check — on a real ledger that has journals and tags
but no transactions yet, an accidental Development start is destructive, not cosmetic.

Restore the original `.env` afterwards and confirm `git status --porcelain` still shows no `.env`
entry.

**Documentation append — `.env.example`.** Add the rules that were just verified, as comments
next to the relevant variables: the password must appear in two places and must match exactly;
in the connection string a password containing a semicolon or an equals sign must be wrapped in
double quotes, while the database container's copy must not be; and the app service's runtime
mode is pinned by `compose.yaml`, so a value set here does not change the deployed stack. Commit
no real password — placeholders only. Append; do not restructure or remove anything Phase 1
committed.

Do not add a Docker secret file, a `_FILE`-suffixed variable, or discrete `POSTGRES_*` variables
for the API side: that trade-off was weighed and rejected in Phase 1 (D-13) and the resulting
exposure is recorded as accepted risk R-01. This task inherits that decision rather than
revisiting it.
